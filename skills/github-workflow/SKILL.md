# GitHub Workflow

Prefer small, reversible, reviewable changes.

## Before changing files
Run/inspect:
- current branch;
- `git status`;
- remote;
- recent commits;
- uncommitted work.

Never discard local changes without explicit intent.

## Branching
For non-trivial work:
`feature/<short-name>`
`fix/<short-name>`
`docs/<short-name>`

Small course repos may work directly on the main branch only if that is the team's established workflow.

## Commit discipline
One commit should represent one logical change.

Good:
- `feat: add mq2 alarm threshold logic`
- `fix: correct decoder enable polarity`
- `docs: add fraud evaluation formulas`

Avoid:
- `update`
- `fix stuff`
- mixing unrelated code, reports, generated files, and experiments.

## Safe staging
Prefer selecting intended files:
`git add path/to/file`

Review:
`git diff --staged`

Do not blindly stage secrets, build outputs, datasets, VM images, or IDE caches.

## Sync workflow
Before push/merge:
1. commit or deliberately stash local work;
2. fetch;
3. inspect divergence;
4. merge/rebase according to team policy;
5. resolve conflicts;
6. build/test;
7. push.

## Conflict resolution
For each conflict:
- understand both sides;
- remove conflict markers;
- preserve required behavior;
- rebuild/retest.

Do not automatically choose `ours` or `theirs` without understanding content.

## Pull request readiness
A PR/change set should answer:
- What changed?
- Why?
- How was it tested?
- Any hardware/setup requirement?
- Any known limitation?

Keep changes narrow enough to review.

## Repository hygiene
Common ignores for engineering coursework:
- build outputs;
- `.vscode`/IDE-local files when not intentionally shared;
- Python caches;
- virtual environments;
- generated waveform/temp files;
- secrets;
- very large raw datasets unless the repository intentionally stores them.

Do not ignore source, constraint, notebook, or reproducibility files merely because they are generated by a tool.
